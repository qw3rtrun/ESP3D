# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ESP3D 3.x: Arduino-framework firmware for ESP8266/ESP8285 and ESP32 (classic, S2, S3, C3, C6). It sits between a 3D printer / CNC / sand table controller (Marlin, Repetier, Smoothieware, GRBL, grblHAL) and the network: WiFi/Ethernet/Bluetooth, HTTP + WebSocket (serves ESP3D-WEBUI), Telnet, FTP, WebDAV, notifications, SD/flash filesystems, display, camera, Lua, and more. User docs live at esp3d.io. The default branch is `3.0-cfg`; use it as the base for branches and PRs. The version is in `esp3d/src/include/esp3d_version.h`.

## Build

The build runs on PlatformIO (`platformio.ini`, `src_dir = esp3d`, `build_dir = .pioenvs`, bundled libs in `libraries/`). Arduino IDE builds also work through `esp3d/esp3d.ino`.

```sh
pio run -e esp32dev              # build one env (others: esp32-s2, esp32-s3, esp32-c3, esp32-c6, esp8266dev, esp8266_1MB_wifi, esp8266_4MB_wifi, esp01s_160mhz, esp8285, esp32cam, esp32_4_4_7 [core 2.x])
pio run -e esp32dev -t upload
pio run -e esp32dev -t uploadfs  # upload esp3d/data to flash FS
pio device monitor -e esp32dev   # 115200
```

- CI (`.github/workflows/build-ci.yml`, `.github/ci/build-esp3d.sh`) builds esp32dev, esp32-s2, esp32-s3, esp32-c3 and esp8266dev with PlatformIO, and also runs Arduino builds for ESP32 and ESP8266. For the ESP8266 Arduino build, CI comments out `DISPLAY_DEVICE` and `ETH_FEATURE` in `configuration.h` first.
- The project has no unit tests. Check a change by compiling it for both an ESP32 env and an ESP8266 env, since most code is `#if`-guarded per platform and per feature.
- `platformIO/extra_script.py` runs before every build. When `configuration.h` sets `SD_DEVICE ESP_SDFAT2`, it adds `extra-libraries/ESP32` or `extra-libraries/ESP8266` (SdFat2) to the lib path.
- Formatting: run `python tools/format_sources.py`. It applies `clang-format -i --style=Google` to every file under `esp3d/`.

## Configuration is compile-time

The firmware is configured mainly through `esp3d/configuration.h`. It is usually generated by ESP3D-Configurator (https://luc-github.github.io/), and `platformio.ini` may be generated by it too. That file turns features on and off with `#define`s such as `WIFI_FEATURE`, `HTTP_FEATURE`, `SD_DEVICE`, `DISPLAY_DEVICE` and `COMMUNICATION_PROTOCOL`. On this branch, local settings that differ from upstream `3.0` go in `esp3d/myconfig.h`, which is committed here (upstream git-ignores it). `configuration.h` includes it at the very top, so it can only *enable* options that `configuration.h` leaves commented out. Changing a value (such as `DEFAULT_FW`) or turning off an option `configuration.h` defines (such as `DIRECT_PIN_FEATURE`) has to be done in `configuration.h` itself. Keep `configuration.h` otherwise identical to `3.0`.

- `esp3d/src/include/esp3d_config.h` is the header every source file includes. It pulls in `configuration.h`, or `esp3dlib_config.h` when the code is built as ESP3DLib inside Marlin. It also pulls in `esp3d_defines.h`, `esp3d_hal.h`, `esp3d_log.h`, `esp3d_pins.h`, `esp3d_sanity.h` and `esp3d_version.h`, and it derives aggregate flags such as `RECOVERY_FEATURE` and `CONNECTED_DEVICES_FEATURE`.
- `esp3d_sanity.h` holds the `#error` checks for invalid feature combinations. Add a check there when you add a constraint.
- Nearly every module, command and handler is wrapped in feature `#if`s. When you add code, match the guards around it in the header, the `.cpp` file and any call sites, or the build breaks for some configurations.
- Logging: the `esp3d_log` / `esp3d_log_d` / `esp3d_log_e` macros in `core/esp3d_log.h` compile to nothing unless `ESP_LOG_FEATURE` and `ESP3D_LOG_LEVEL` are set in `configuration.h`.

## Architecture

The `esp3d.ino` entry point creates a single `Esp3D` object (`src/core/esp3d.cpp`) and calls its `begin()` and `handle()` methods. `begin()` loads settings, starts serial/USB, and then starts the network services (`modules/network/netservices.cpp`). `handle()` polls every enabled module.

**Messages and clients.** Every piece of data moving through the firmware is an `ESP3DMessage` (`core/esp3d_message.h`). A message carries a data buffer, an `origin` and a `target` (`ESP3DClientType` in `core/esp3d_client_types.h`: serial, usb_serial, telnet, http, webui_websocket, websocket, bluetooth, mks_serial, lua_script, rendering, remote_screen, all_clients, …), plus an authentication level, a request id (which holds the `WebServer*` for HTTP) and a type (`head/core/tail/unique/realtimecmd`). Messages are allocated and freed through `esp3d_message_manager`, and whoever consumes a message must delete it.

**Commands (`core/esp3d_commands.*`, global `esp3d_commands`).** Each module passes its incoming data to `esp3d_commands.process(msg)`:
- If the data is an `[ESPxxx]` command, `execute_internal_command()` dispatches it by number to `ESPxxx()`. Each of those is implemented in its own file, `core/commands/ESPxxx.cpp`, and is declared in `esp3d_commands.h` under that command's feature guard. Shared helpers handle parameter parsing (`get_param`, `has_param`, `hasTag`, `get_clean_param`) and replies (`dispatchAnswer`, `dispatchSetting`, `dispatchKeyValue`, `dispatchIdValue`, `format_response`, with plain-text or `json` output).
- Anything else goes to `dispatch(msg)`, which forwards it to the module for `msg->target`, such as the serial service, telnet server or websocket server. Each of those modules has its own `dispatch()`. The "output client" (serial, USB serial or MKS) is the link to the printer.
- The command syntax and the full command list are documented in `docs/Commands.md`. A new command needs a `case` in `execute_internal_command`, a declaration in the header, a new `ESPxxx.cpp` file, and an update to `docs/Commands.md`.

**Settings (`core/esp3d_settings.*`).** Settings are addressed by integer offsets (`ESP_*` defines in `include/esp3d_defines.h`, for example `ESP_BOOT_RADIO_STATE 1221`). They are stored in EEPROM or in ESP32 Preferences, chosen by `ESP_SAVE_SETTINGS`. Access goes through the static `ESP3DSettings::read*/write*` methods. Defaults and the list of valid settings come from the `ESP3DSettingsData[]` table in `esp3d_settings.cpp`. `CURRENT_SETTINGS_VERSION` there controls when stored settings get reset. `ESP400` exposes the settings to the WebUI, and `ESP401` writes them.

**Modules (`esp3d/src/modules/`).** Each subsystem has its own directory and usually exposes a global service object. A few cross-cutting pieces:
- `http/`: `http_server.cpp`, plus one file per route in `http/handlers/`. `http/embedded.h` is a generated gzipped page.
- `filesystem/`: flash filesystems (`flash/`, LittleFS/SPIFFS/FAT) and SD drivers (`sd/`) behind `esp_filesystem` and `esp_sd`, with `esp_globalFS` as a unified view.
- `authentication/`: the `ESP3DAuthenticationLevel` checks used by the commands and the HTTP server.
- `mks/`: the MakerBase serial protocol, which replaces the raw serial protocol when `COMMUNICATION_PROTOCOL` is `MKS_SERIAL`.

**HAL.** `core/esp3d_hal.*` wraps the differences between ESP8266 and ESP32 and between Arduino core versions (watchdog, delays, pin access). Use it instead of calling the cores directly.

## Embedded fallback page

`embedded/` is a small webpack project. It builds the fallback page that is served when the WebUI is not on the filesystem.

```sh
cd embedded && npm install
npm run build   # pack -> gzip -> regenerates esp3d/src/modules/http/embedded.h (and favicon assets)
npm run dev     # local dev server + mock ESP backend (config/server.js)
```

Do not hand-edit `embedded.h` or `favicon.h`.

## Tools

- `tools/fw_simulator/fw_simulator.py <port>`: pyserial-based simulator of Marlin/GRBL/grblHAL/Repetier/Smoothieware printer firmware, for testing the serial side without a printer.
- `tools/wsterm.html` and `tools/printer.py`: WebSocket terminal and serial helpers.
- `lua_script_examples/`: sample scripts for the Lua interpreter module.
